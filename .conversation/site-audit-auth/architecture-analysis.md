Verdict: the audit establishes a clear, high-impact rebuild opportunity—the present application preserves broad CRM behavior but has an excessively global, heavyweight client shell and server-circuit startup path.

**Verified facts**
- This is ASP.NET/Blazor Server behind IIS: server-rendered Blazor descriptors, `blazor.server.js`, and authenticated WebSocket connections to `/_blazor` are captured. The UI combines MudBlazor, Microsoft Fluent web components/Fabric, Bootstrap (including RTL), Syncfusion PDF, Chart.js, Firebase scripts, CKEditor, Mapbox, jQuery, and custom JS.
- The unauthenticated login fetches 50 resources / 13.24 MB transferred (14.37 MB decoded) before it can complete. DCL/load are ~4.36 s despite 134 ms TTFB. The largest avoidable initial resources are Syncfusion CSS (2.81 MB), two PDF viewer scripts (~2.77 MB each), CKEditor (~760 KB), Mapbox (~405 KB), and both Fabric CSS files (~626 KB, apparently duplicate variants). All are included on login.
- Authenticated route captures are also slow: 81 measured navigations have 16.24 s median elapsed time (9.8–49.1 s). These timings include audit/navigation conditions, so they prove poor observed UX, not isolated backend latency.
- The product has a persistent navigation shell and operational areas for dashboard, users/workplaces, inventory, purchases, sales, accounting, reports, deletion logs, and transaction/detail forms. It supports RTL Kurdish UI, language switching, light/dark/fullscreen controls, tables, filtering/sorting, print/PDF and some infinite-scroll integration. Login has a responsive two-column composition that hides its decorative image below the large breakpoint; the 390px capture has no horizontal overflow. Authenticated mobile behavior was not captured.

**Inference / unknowns**
- Blazor Server means interaction latency and capacity are coupled to long-lived SignalR circuits and server memory/CPU; this is likely a material contributor under latency/concurrency, but database/query, rendering, and API timings were not captured. Firebase/Mapbox usage is evidenced by global assets, not by actual feature invocation. Data model, authorization enforcement, real record volume, and mobile authenticated layouts are unknown.

**Security/header observations**
No confirmed serious vulnerability. HTTPS and HSTS (30-day max-age) are verified. The only captured headers are for the 302 redirect and show no CSP, frame-ancestors/X-Frame-Options, Referrer-Policy, Permissions-Policy, or nosniff; final authenticated response headers, cookie flags, CSRF/authz behavior, and endpoint authorization were not audited. IIS/ASP.NET version disclosure is present.

**Recommended faster rebuild**
1. Build a modular, route-chunked web client (React/TypeScript or Blazor WASM) over a versioned BFF/API, retaining shared RTL-aware shell, locale catalog, theme tokens, and domain modules. Load editor, maps, charts, PDF/export, image compression, and Firebase only in the routes that use them; use one design system rather than the current overlapping three.
2. Make list/report endpoints server-paginated, filtered/sorted, projection-based, and indexed; virtualize grids and fetch dashboard aggregates independently/cached. Preserve transaction writes with explicit validation, idempotency, role/workplace scoping, and audit logs.
3. Serve hashed static assets via CDN with long immutable caching while keeping authenticated HTML/API private; establish performance budgets (login well below 1 MB) and capture RUM/API traces before data migration. Validate final headers, secure cookies, CSRF, and per-record authorization before cutover.
